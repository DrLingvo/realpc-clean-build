# Разбор закрытых сборок «Strong»

## OVMF: `pve-edk2-firmware-ovmf_4.2026.08-1_all_Strong.deb`

MD5 файла `a9d2903b4238507357051cc2104b2628` (совпадает с лежащим в репозитории автора).

Метод:
1. `OVMF_CODE_4M.fd` из обычного и Strong-пакетов автора распакованы `uefi-firmware-parser`
   (131 PE-модуль в каждом, набор и GUID совпадают).
2. Для каждого модуля сравнивались секции `.text`/`.data`. Перед сравнением маскировались
   два источника шума пересборки:
   - stack-cookie, который edk2 случайно генерирует при каждой сборке (4 байта в PEI, 8 в DXE:
     `6e581a7d…` и `3c1fa1d6…`);
   - XIP-перебазирование PEI-модулей: все расхождения в `PlatformPei`, `CpuMpPei`, `Tcg2Pei`,
     `TcgPei`, `DxeIpl`, `S3Resume2Pei` — абсолютные адреса со сдвигом на постоянную величину
     (`-0x100`, `-0x180`, `-0x40`), потому что `.data` у ряда модулей на 64 байта короче
     (выравнивание другой сборки).
3. После этого функциональные отличия остались **только в `QemuVideoDxe`** (у автора называется
   `DellVideoDxe`), в таблице `gQemuVideoCardList`:

   | Устройство | Обычная | Strong |
   |---|---|---|
   | QEMU Standard VGA (primary/secondary) | 0x1234:0x1111 | 0x6666:0x1111 |
   | QEMU VirtIO VGA | 0x1af4:0x1050 | 0x8085:0x1050 |
   | QEMU VMWare SVGA | 0x15ad:0x0405 | 0x8085:0x0405 |

   Код драйверов virtio (`Virtio10Dxe`, `VirtioPciDeviceDxe` и др.) не изменён: они по-прежнему
   ищут 0x1af4. Следовательно, загрузка с virtio-дисков под Strong-QEMU невозможна, что
   согласуется с рекомендацией автора использовать SATA.

Воспроизведение: `STRONG_PCI_IDS=1` → `edk2/anti-detection.sh` (таблица) и
`qemu/strong-pci-ids.sh` (сами устройства в QEMU).

В обоих OVMF автора производитель прошивки — «Proxmox distribution of EDK II», версия «4.2026.08-1».

## QEMU: `pve-qemu-kvm_11_1_3-3_amd64.deb` (присланный файл)

MD5 `c3c964b82f6c9ea06e3e7c51d158fd3b`. Это **не Strong**, а обычная сборка автора:
- все пути исходников, встроенные в бинарник (`../hw/...c`, 1135 шт.), есть в штатном
  QEMU 11.1.3 + патчах Proxmox, новых файлов нет;
- `qemu-vmsr-helper` штатный: белый список MSR = база 0x606, маска 0x4c01 →
  0x606/0x610/0x611/0x614 (только RAPL), как в upstream;
- обращений к `/sys/class/hwmon`, `/dev/cpu/*/msr` (кроме vmsr-helper) и т. п. нет;
- метки из опубликованных скриптов присутствуют (`DELL-%04d-aiiaicodo`, `aiiaicodo PowerS…`,
  `LGA1700`, `KHX1600C9S3L/32G`).

Для разбора проброса датчиков нужен именно `*_Strong.deb` QEMU.

## SeaBIOS (`pc-bios/bios*.bin` автора)

В репозитории лежит патч «для справки» (`seabios-autoGenPatch.patch`). Он меняет ID Q35 MCH/LPC
на 0xdd66/0xdd88, то есть рассчитан на QEMU с изменёнными ID Q35. OVMF Strong таких изменений не
содержит (`PlatformPei` идентичен), поэтому в этом наборе ID возвращены к стандартным.

## Сверка с реальной сборкой автора (`qemu-autoGenPatch.patch`, релиз v20261120-211494-pve9-x64)

SHA256 `22d55e23…09ff42`, скачан с Releases. Это полный diff исходников QEMU из CI-сборки автора.
Он чисто накладывается на pve-qemu 11.1.3-4. Дерево «патч автора» сравнено с деревом
«этот набор» (`anti-detection.sh` + `smbios.patch` + правка igd.c). Отличаются только:
- значения меток (серийники, SMART, SAS, USB) — у нас из `config.env`;
- три утечки, которые у автора остались, а у нас закрыты: модель CPU «QEMU Virtual CPU»,
  ревизия прошивки IDE/SCSI-дисков `2.5+` (`QEMU_HW_VERSION`), версия SMBIOS type 1 = имя машины;
- принудительный bootsplash (у нас опция `BOOTSPLASH_JPG`, по умолчанию выключена);
- комментарии и пробелы.
Других изменений в сборке автора нет.

## Где Strong-версия QEMU

По всем 79 тегам репозитория проверены варианты имени `pve-qemu-kvm_<версия>_amd64_Strong.{deb,7z,zip,rar}`,
ничего не найдено. В истории git его тоже нет, в соседнем репозитории `AICodo/qemu-emu-realpc`
(патчи под QEMU 6.2–11.0) кода датчиков нет. Вывод: Strong-версия QEMU на GitHub не опубликована.
